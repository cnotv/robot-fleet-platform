Robot Fleet Platform architecture

A real time resource management system that ingests telemetry from 1,000 concurrent robots, keeps the latest state of every robot in memory, and streams it to a browser dashboard without dropping frames.

GoNode.js + TypeScriptNext.jsRedisPostgreSQLMongoDB

Overview

The platform is a monorepo with three decoupled services. They share no code and talk only through Redis and HTTP or WebSocket, so each can be built, scaled and replaced on its own.

Components

Ingestion service

Go, net/http, gorilla/websocket, go-redis

  • One goroutine per robot connection.
  • Accepts one frame per 500ms per connection; extra frames get a throttled ack.
  • Strict decoding: unknown fields, missing fields and out of range values are rejected.
  • The robot_id in the body must match the id in the URL.
  • Adds ingested_at and publishes to robot:telemetry:live.
  • Stateless, so it scales horizontally behind any TCP or HTTP load balancer.

Orchestration API

Node.js 20, TypeScript, Express 5, Prisma, Mongoose, ioredis, ws

  • JWT login backed by PostgreSQL users with roles.
  • Subscribes to the telemetry channel and batches every 250ms.
  • Each batch: one HSET, one broadcast frame, one unordered bulk insert.
  • Serves the full fleet snapshot straight from the Redis hash.
  • Logs errors to the ErrorLog collection.

Fleet dashboard

Next.js App Router, React, Tailwind, Zustand, TanStack Virtual, lucide-react

  • Zustand store buffers socket frames and commits to React every 300ms.
  • Reconnects reload the snapshot, so missed frames are resynced.
  • Canvas map repaints in requestAnimationFrame and never re-renders React.
  • Robot table renders only the rows inside the viewport.

Telemetry flow

A packet travels from robot to pixel in about half a second in the worst case: up to 250ms waiting for the API batch plus up to 300ms waiting for the dashboard flush.

Dashboard start up

  1. The user signs in with POST /api/auth/login and gets a JWT, kept in sessionStorage.
  2. The store calls GET /api/fleet/snapshot to load all 1,000 robots at once.
  3. It opens /ws/fleet?token= and merges incoming batches, ignoring any update older than what it already holds.
  4. If the socket drops, it waits 2s, reloads the snapshot and reconnects. A 401 on the snapshot sends the user back to the login page.

Contracts

Robot packet (robot to ingestion)

{
  "robot_id": "rob-v-10049",
  "status": "active",              // active | charging | error | idle
  "telemetry": {
    "latitude": 48.1351,           // [-90, 90]
    "longitude": 11.5820,          // [-180, 180]
    "speed_mps": 1.2,              // [0, 50]
    "battery_pct": 84.5            // [0, 100]
  },
  "current_task": "floor_scrub_zone_b",   // [A-Za-z0-9_.:-], up to 128 chars
  "timestamp": "2026-09-24T00:00:00Z"     // RFC 3339, at most 30s in the future
}

A frame may also be a JSON array of up to 5 packets. Each frame is answered with {"ok":true} or {"ok":false,"error":"..."}.

Redis: hot state and messaging

Redis is the only shared runtime dependency between ingestion and the API. It holds nothing that cannot be rebuilt: the hash refills within one second of robots reporting.

Security model

  • Robots are unauthenticated by design. Strict validation limits damage, but any client that can reach the ingestion endpoint can report for any robot id. Restrict it at the network edge (private network, VPN, IP allow list or mTLS) before exposing it.
  • Users sign in with bcrypt hashed passwords and receive an HS256 JWT valid for 8 hours. JWT_SECRET must be a long random value in every shared environment.
  • Dashboard socket carries the JWT in the query string, because browsers cannot set headers on a WebSocket. Keep query strings out of proxy access logs.
  • CORS allows exactly one origin, CORS_ORIGIN.
  • Databases are published on 127.0.0.1 only by the compose file and are never meant to be reachable from outside the host or private network.

Operations

  • Health: GET /healthz on ingestion and API returns 204.
  • Logs: ingestion writes JSON lines to stdout; the API writes to stdout and to the errorlogs collection.
  • Schema: the API container runs prisma db push on boot.
  • Load test: go run ./cmd/simulator -n 1000 -url wss://robots.example.com drives a fleet from any machine.
  • Tests: go test -race ./... in ingestion; npm test in the API cover handshakes, throttling, sanitization and telemetry mapping.

Known limits

  • Ingestion has no device authentication.
  • Login has no rate limiting.
  • The orchestration API must run as a single replica.
  • Schema changes use db push; move to prisma migrate deploy once migrations exist.
  • RobotState is declared in both the API and the dashboard.
